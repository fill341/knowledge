# Оценка поиска (`kn eval`)

Измеряет, находит ли база то, что нужно агенту. Без этих цифр нельзя честно менять ранжирование
или решать, нужны ли embeddings (roadmap P1 #3, [docs/roadmap.md](../docs/roadmap.md)).

## Как устроено

Набор — JSON-файл с запросами и ожидаемыми записями. `kn eval` отправляет его в `POST /v1/eval`. Сервер прогоняет
каждый запрос через тот же код поиска (`kn_search`) и контекста (`kn_context`), что и у агентов, в пределах видимости
токена. В аудит пишется одно событие `eval`, а не поиски, поэтому статистика использования и отчёт о здоровье не искажаются.

| Метрика | Что значит |
|---|---|
| `recall@5`, `recall@k` | доля ожидаемых записей в первых 5 / k результатах поиска |
| `MRR` | среднее 1/ранг первой ожидаемой записи (1 — всегда первая, 0 — не найдена) |
| `пустых` | доля запросов без единого результата |
| `контекст` | доля ожидаемых записей, попавших в `kn_context` под бюджет токенов |
| `досягаемо` | доля ожидаемых записей в контексте или в его оглавлении «Не поместились» (агент может открыть их `kn_get`) |

## Формат набора

```json
{
  "project": "personal/knowledge",
  "k": 10,
  "max_tokens": 6000,
  "cases": [
    { "id": "ports", "query": "на каком порту веб-интерфейс", "mode": "both",
      "expect": [ { "title": "Где что живёт в локальной установке kn" } ],
      "note": "необязательная заметка, печатается рядом с промахом" }
  ]
}
```

- `project` в корне — проект по умолчанию для запросов без своего.
- `mode`: `search`, `context` или `both` (по умолчанию).
- `no_task: true` — контекст без задачи, как при старте сессии (хук); `query` тогда служит только подписью.
- `expect` — список ожидаемых знаний. Каждое задаётся одним из ключей: `id`, `source_ref`, `title`
  (точный заголовок без учёта регистра). Знание считается найденным, если найдена любая из подходящих записей:
  например, один документ, импортированный дважды.
- Если ожидание не соответствует ни одной видимой живой записи, это ошибка разметки. Такой запрос исключается
  из метрик и печатается с `?`. Так видно, что разметка устарела: запись заменили или архивировали.

Запросы формулируйте так, как агент описывает задачу или симптом, а не копией заголовка. Иначе метрика
измеряет совпадение заголовков, а не поиск.

## Наборы

| Набор | Где | Для чего |
|---|---|---|
| Фикстура | `services/knowledge-api/internal/httpapi/testdata/eval_fixture.json` | Синтетический корпус и запросы. Гоняется в `make test` на временной БД; поле `min` — порог регрессии |
| Рабочий | `eval/local/queries.json` (в `.gitignore`) | Запросы к рабочей базе. Ссылаются на личные и рабочие записи, поэтому в git не попадают |
| Пример | [example.json](example.json) | Формат |

## Команды

```sh
kn eval                         # eval/local/queries.json, сравнение с eval/local/baseline.json
kn eval --all                   # показать все запросы, а не только промахи
kn eval --save-baseline         # зафиксировать текущие метрики как базовую линию
kn eval -f my.json --tolerance 0.01
```

Код выхода 1, если любая метрика хуже базовой линии больше допуска (по умолчанию 0,02).
Любое изменение поиска или контекста проверяется прогоном до и после.
