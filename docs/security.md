# Безопасность и изоляция

## 1. Модель угроз (локальная установка)

| Угроза | Пример | Защита |
|--------|--------|--------|
| Утечка между профилями | Агент в Work-профиле читает Personal-заметки и выносит их в рабочий репозиторий | Токены со scope'ами по пространствам, проверка в store-слое, тесты изоляции |
| Prompt injection | Вредоносный текст в репозитории заставляет агента записать мусор или вытащить данные | Агент видит только своё пространство; записи агентов важных типов идут через review; rate limit; аудит |
| Секреты в знаниях | Агент сохраняет `.env` или токен в заметку | Сканер секретов на каждой записи, `422` без возможности обхода для агентов |
| Доступ из сети | API случайно доступен в Wi-Fi сети | Порты привязаны к `127.0.0.1`, БД не публикуется наружу |
| Прямой доступ к БД | Агент находит пароль и подключается к PostgreSQL | У агентов нет учётных данных БД; пароли — только в Docker secrets |
| Потеря/порча данных | Баг, `docker compose down -v`, сбой диска | История версий, запрет DELETE на уровне прав, ежедневные дампы, проверка восстановления |
| Утечка бэкапа | Дамп попал в облачную синхронизацию | Каталог бэкапов вне синхронизируемых папок; опционально шифрование `age` |

## 2. Пространства и права

### Scope'ы

Формат: `space:<slug>:<level>`, уровни иерархичны: `read` < `write` < `review` < `admin`. Плюс глобальный `admin`.

| Уровень | Разрешено |
|---------|-----------|
| `read` | Поиск, контекст, чтение записей и истории, экспорт |
| `write` | + создание/правка записей и проектов, связи, сессии |
| `review` | + approve/reject, восстановление из `archived` |
| `admin` (space) | + настройки пространства |
| `admin` (глобальный) | + principals, токены, типы записей, аудит |

### Рекомендуемая матрица токенов

| Principal | personal | work | shared |
|-----------|----------|------|--------|
| `me` (человек, CLI / Web UI) | admin | admin | admin |
| `claude-code@personal`, `cursor@personal`, `bb@personal` | write | — | read |
| `claude-code@work`, `cursor@work`, `codex@work`, `bb@work` | — | write | read |
| `obsidian-sync@personal` | write | — | read |

**Почему агенты по умолчанию только читают `shared`:** `shared` видят оба профиля. Если Work-агент может писать в `shared`,
рабочая информация через него попадает в Personal-контекст (и наоборот). Перенос в `shared` — осознанное действие человека
через `promote`, видимое в аудите. Если нужно, `shared:write` можно выдать конкретному агенту — но записи в `shared` от агентов
тогда всегда идут как `proposed`.

### Где проверяются права

1. **Middleware** — аутентификация: поиск по `prefix`, сравнение `sha256(secret)` в постоянное время, проверка `revoked_at`, `expires_at`, `principals.disabled_at`. Результат — `Principal` + `Scope` в контексте запроса.
2. **Store-слой** — каждая функция чтения принимает `Scope` и добавляет `space_id = ANY($allowed)` в SQL. Функции без `Scope` не существует — обойти проверку случайно нельзя.
3. **Domain-слой** — переходы статусов и требование review зависят от типа principal (`agent` / `user`) и уровня scope.
4. **Фаза 2: Row Level Security** — второй рубеж. Сервис в начале транзакции делает `SET LOCAL app.space_ids = '...'`, политики RLS на `entries`, `projects`, `entry_versions` фильтруют по нему. Даже ошибка в store-слое не отдаст чужие строки.

**Обязательные интеграционные тесты изоляции** (часть MVP, гоняются в CI/`make test`):
- Work-токен: `GET /v1/entries/{personal_id}` → `404`; поиск по уникальному слову из personal-записи → пусто; `/v1/context` не содержит personal; `export?space=personal` → `403`.
- Агентский токен не может `approve`, не может выпустить токен, не может `revert` в обход `If-Match`.

## 3. Токены

- Формат: `kn_<prefix>_<secret>`; `prefix` — 8 символов base62 (виден в логах и `kn token list`), `secret` — 32 байта из `crypto/rand`, base62.
- В БД хранится только `sha256(secret)`; секрет показывается один раз при выпуске.
- Высокая энтропия секрета делает медленный хэш (bcrypt/argon2) ненужным, а проверка на каждый запрос остаётся дешёвой.
- `last_used_at` обновляется не чаще раза в минуту (чтобы не писать на каждый запрос).
- Опциональный `expires_at`; отзыв — `revoked_at`, действует мгновенно.
- Префикс `kn_` позволяет добавить правило в сканеры секретов (gitleaks и т. п.), чтобы токен не попал в git.

## 4. Хранение credentials

| Секрет | Где хранится | Кто видит |
|--------|--------------|-----------|
| Пароль `kn_owner` (владелец схемы) | `deploy/secrets/pg_owner_password` → Docker secret | postgres, migrate, backup |
| Пароль `kn_app` (рантайм) | `deploy/secrets/pg_app_password` → Docker secret | postgres (init), knowledge-api |
| Токены агентов | macOS Keychain (`security add-generic-password -s kn-token -a <principal>`) | `kn-mcp-launch`, `kn` CLI |
| Admin-токен человека | Keychain | `kn` CLI |
| Ключ шифрования бэкапов (опц.) | Keychain / менеджер паролей, вне репозитория | только при восстановлении |

- `deploy/secrets/` в `.gitignore`, права `600`; создаётся `make secrets` (случайные пароли через `openssl rand`).
- Никаких секретов в `docker-compose.yml`, `.env`, `.mcp.json`, `config.toml` — только ссылки на файлы/Keychain.
- Сервис читает пароли из `*_FILE` переменных, а не из env-значений (не видны в `docker inspect`).
- Опционально: хранить `deploy/secrets` зашифрованными (`sops` + `age`) или брать из 1Password CLI — интерфейс тот же, меняется только `make secrets`.

## 5. Сканер секретов в записях

Выполняется для `title`, `summary`, `body`, строковых значений `attributes` при создании, изменении и импорте.

- Правила: приватные ключи (`-----BEGIN ... PRIVATE KEY-----`), AWS (`AKIA...`), GitHub (`ghp_`, `github_pat_`), GitLab (`glpat-`), Slack (`xox[abpr]-`), OpenAI/Anthropic-подобные ключи (`sk-...`), JWT, токены `kn_`, URL с паролем (`scheme://user:pass@`), строки вида `password|secret|token\s*[:=]\s*<высокоэнтропийное значение>`.
- Срабатывание → `422 secret_detected` с полем и позицией, **без** найденного значения в ответе и логах.
- Обход: только человек с `review` через `allow_secret_patterns: ["<rule-id>"]` (для документации о форматах ключей), фиксируется в аудите. Агентам недоступно.

## 6. Аудит

- Пишутся все изменения (create/update/transition/promote/review/link/import), выпуск и отзыв токенов, неудачные аутентификации.
- Чтения: `search` и `context` — с hash запроса, числом результатов и пространствами (без текста запроса и результатов); `GET` отдельных записей — опционально (`KN_AUDIT_READS=true`).
- `audit_log` — append-only на уровне прав БД.
- Метрика для решения о embeddings: доля поисков с 0 результатов и поисков, за которыми не последовал `kn_get`.

## 7. Прочее

- Rate limit на запись: 60 записей/мин на токен — защита от зациклившегося агента.
- Лимиты размера: тело запроса 1 МБ, `body` ≤ 200 000 символов.
- `knowledge-api` в distroless-образе, non-root, read-only rootfs.
- Диск хоста зашифрован (FileVault) — данные БД в Docker volume не шифруются отдельно.
