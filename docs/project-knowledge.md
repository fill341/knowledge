### Одна БД с пространствами personal/work/shared вместо отдельных инстансов

<sub>`01a1e80d-8350-729a-8c45-96e641ca3fd6` · обновлено 2026-11-17 · теги: architecture, security, isolation</sub>

> Один PostgreSQL, таблица spaces, у каждой записи space_id; токены агентов ограничены scope'ами space:<slug>:<level>. Store-слой принимает Visibility в каждом чтении, изоляция покрыта интеграционными тестами. Агенты по умолчанию только читают shared — перенос туда делает человек через promote.

##### Контекст

Нужна изоляция Personal/Work/Shared и при этом единый источник знаний; shared должен быть виден обоим профилям.

##### Решение

Один PostgreSQL, таблица spaces, у каждой записи space_id; токены агентов ограничены scope'ами space:<slug>:<level>. Store-слой принимает Visibility в каждом чтении, изоляция покрыта интеграционными тестами. Агенты по умолчанию только читают shared — перенос туда делает человек через promote.

##### Альтернативы

- Отдельный инстанс БД на Personal и Work — физическая изоляция, но shared и единый источник становятся сложными; оставлен как запасной вариант (второй compose-проект), если потребует работодатель
- Row Level Security как основной механизм — отложено как второй рубеж (фаза 2)

##### Последствия

Изоляция логическая: держится на store-слое и тестах. Если Work-агент получит запись в shared, рабочие данные утекут в Personal-контекст — поэтому write в shared агентам не выдаётся.

### Без кодогенерации: OpenAPI как контракт, сервер, клиент и SQL пишутся руками

<sub>`01a1e80d-8360-759d-9c00-9658f8606a7f` · обновлено 2026-11-17 · теги: architecture, go, api</sub>

> api/openapi.yaml остаётся контрактом и проверяется redocly lint (make lint). Хендлеры на net/http (паттерны Go 1.22+), SQL на pgx в internal/store, клиент pkg/kclient и мигратор (embed + schema_migrations + advisory lock) — без генераторов. Соответствие контракту держат интеграционные тесты API.

##### Контекст

В дизайне планировались oapi-codegen, sqlc и goose. Эндпоинтов ~40, разработчик один, всё локально.

##### Решение

api/openapi.yaml остаётся контрактом и проверяется redocly lint (make lint). Хендлеры на net/http (паттерны Go 1.22+), SQL на pgx в internal/store, клиент pkg/kclient и мигратор (embed + schema_migrations + advisory lock) — без генераторов. Соответствие контракту держат интеграционные тесты API.

### Сначала полнотекстовый поиск PostgreSQL, embeddings — только по метрике промахов

<sub>`01a1e80d-836a-75f1-b277-2de99588d706` · обновлено 2026-11-17 · теги: architecture, search, postgres</sub>

> FTS 'russian' + добор по заголовкам и по части слов. Гибридный поиск (embeddings) — только по kn eval: на 2026-11-17 recall@10 0,912, пустых 0 % — не нужен. Вернуться, если recall@10 < 0,85 или MRR < 0,6 на ≥ 60 размеченных человеком запросах, и промахи — синонимы/перефразировки.

##### Контекст

Постановка требует не начинать с RAG до реальной необходимости; знания на русском и английском.

##### Решение

FTS с конфигурацией 'russian' (title A, summary B, body и строки attributes C); если поиск по всем словам дал < 3 записей — добор похожими заголовками (pg_trgm) и записями с любым словом запроса (см. «Поиск по части слов как фолбэк FTS вместо embeddings»). pgvector установлен, таблица чанков не создаётся.

Решение о гибридном поиске принимается по `kn eval`, а не по доле пустых поисков в аудите. Замер 2026-11-17 (34 запроса): recall@10 0,912, MRR 0,694, пустых 0 % — гибридный поиск не нужен; оставшиеся промахи (минус в коде ошибки, длинные документы) embeddings не решают.

**Критерий возврата:** recall@10 < 0,85 или MRR < 0,6 на наборе ≥ 60 размеченных человеком запросов, и при этом промахи — синонимы и перефразировки.

##### Альтернативы

- Сразу гибридный поиск с эмбеддингами — зависимость от модели/провайдера и сложность без доказанной пользы
- Отдельный поисковик (Meilisearch и т.п.) — ещё один сервис и синхронизация

##### Последствия

Синонимы и перефразировки FTS не найдёт. Переход к hybrid не меняет API (mode: hybrid зарезервирован).

### MCP-сервер — stateless тонкий клиент REST, токены только в Keychain

<sub>`01a1e80d-8372-7df8-b2b2-79892d90fb63` · обновлено 2026-11-17 · теги: architecture, mcp, security</sub>

> kn-mcp запускается по stdio (из инструмента или через OpenAI tunnel-client для ChatGPT) с токеном из Keychain; stateless, вся логика в knowledge-api. 9 инструментов; проект: KN_PROJECT → git remote cwd → MCP roots → kn_project(path) или kn_context(project=…) со списком проектов.

##### Контекст

Нужно одинаковое поведение для Claude Code, Cursor, Codex, ChatGPT и bb; агенты не должны иметь доступа к БД; токены не должны лежать в конфигах инструментов.

##### Решение

kn-mcp запускается по stdio через scripts/kn-mcp-launch <agent> <profile>, который берёт токен <agent>@<profile> из macOS Keychain (service kn-token): локальные инструменты стартуют его сами, для ChatGPT его стартует OpenAI tunnel-client (scripts/kn-chatgpt-tunnel, только исходящие соединения). Вся логика — в knowledge-api; kn-mcp переводит 9 инструментов в REST (kn_context, kn_project, kn_search, kn_get, kn_save, kn_record_decision, kn_update, kn_link, kn_log_session) и лениво открывает сессию для провенанса. Проект определяется по порядку: KN_PROJECT → git remote рабочей директории → git remote рабочих папок клиента (MCP roots, запрашиваются на initialized и только для протоколов до 2026-07-28) → явный выбор: kn_project(path, create) для локальных репозиториев или kn_context(project=<space>/<slug>) — без выбранного проекта kn_context показывает список доступных. kn_save предупреждает о записи без проекта.

##### Альтернативы

- Общий долгоживущий MCP-сервер со всеми токенами — один процесс знает всё
- MCP с прямым доступом к БД — дублирование правил и обход изоляции
- Определять проект только по cwd — не работает в Cursor (стартует MCP из $HOME) и в ChatGPT (нет локальной папки)
- Открыть базу в интернет для ChatGPT (публичный HTTPS + OAuth) — противоречит local-first

##### Последствия

Новый агент подключается без изменения ядра: principal + токен + конфиг. Ошибки API переводятся в подсказки для модели. После изменений kn-mcp — make build и перезапуск инструмента или туннеля ChatGPT. Данные, прочитанные ChatGPT, уходят в OpenAI — его токен без доступа к work.

### Веб-интерфейс — отдельный BFF-сервис web-ui: токен в зашифрованной HttpOnly-куке, SPA на React

<sub>`01a1e837-2b80-792f-a9e9-9c27f8e1a2fb` · обновлено 2026-11-17 · теги: architecture, web-ui, security</sub>

> Отдельный контейнер web-ui (Go, :8790): встроенная SPA (React + Vite + TS), прокси /api/* → /v1/* с токеном из зашифрованной HttpOnly-куки; CSRF через X-KN-UI; вход только человеком. На «Обзоре» — карта знаний в 3D: «Галактика» (проекты — звёзды, записи — планеты на орбитах по типам) и «Граф связей».

##### Контекст

Ревью и управление токенами через CLI неудобны; нужен локальный UI для проверки записей, поиска, RBAC, аудита и наглядной карты знаний. Токен в браузерном JS — риск (контент от агентов недоверенный, XSS).

##### Решение

Отдельный контейнер web-ui (Go, :8790): раздаёт встроенную SPA (React + Vite + TS) и проксирует /api/* → knowledge-api /v1/*, подставляя токен из куки kn_ui (AES-256-GCM, ключ из deploy/secrets/ui_session_key, 12 ч, HttpOnly, SameSite=Strict). CSRF: обязательный заголовок X-KN-UI на изменяющих запросах + проверка Origin. Вход только токеном человека — агентов UI не пускает. Markdown записей санитизируется DOMPurify, сырой HTML выводится как текст. На «Обзоре» — карта знаний в 3D, два режима (выбор запоминается): «Галактика» на чистом three.js с bloom (проекты — звёзды, записи — планеты на орбитах по типам, документы — пояс астероидов, связи — светящиеся дуги) и «Граф связей» (3d-force-graph). Оба — ленивые чанки. В API добавлены GET /v1/stats, GET /v1/graph (записи + связи между видимыми концами + проекты) и enable/disable principal.

##### Альтернативы

- SPA ходит в API напрямую с токеном в localStorage — токен доступен JS, нужен CORS на API
- Встроить UI в knowledge-api — нарушает принцип «не монолит», ядро не должно знать про UI
- Серверный рендеринг (Go templates + htmx) — проще сборка, но слабее UX для diff версий, модалок, матрицы прав
- Граф в 2D (vis/cytoscape) — проще, но при ~800 узлах и гигантском кластере крупного проекта хуже читаются кластеры-проекты
- Галактика на 3d-force-graph — физика графа не даёт орбит, света и сопровождения камерой

##### Последствия

Сессии сбрасываются при смене ui_session_key. Сборка образа web-ui требует node (multi-stage). Отозвать токен, которым вошёл в UI, — значит выйти; UI предупреждает. Карта ограничена 5000 записями; анимация орбит уважает prefers-reduced-motion и ставится на паузу пробелом.

Агенты видят отчёт через kn_health (только чтение) и предлагают исправления. Доступно также в kn health.

##### Альтернативы

- Embeddings для поиска похожих — преждевременно: точные и триграммные совпадения уже находят основную массу проблем

##### Последствия

Нет миграций и состояния. Стоимость растёт с объёмом (самосоединение по триграммам, хэш нормализованного текста): при десятках тысяч записей понадобятся лимиты или снимки. Пары и группы ищутся внутри пространства — копии между пространствами через promote дублями не считаются. Дальше по roadmap: дедуп по содержимому при записи, тестовый набор запросов (kn eval), сигнал использования, структурированные сессии.

### Переполнение kn_context: правила под потолком 35 %, отбор по задаче, оглавление вместо отсечения, бюджет 10 000, хук 2700 (ADR-10)

<sub>`01a1ea13-7a68-76b8-ba6e-3571b4b63bfb` · обновлено 2026-11-17 · теги: architecture, context, eval</sub>

> Правила ≤ 35 % бюджета; с задачей — единый пул по релевантности; без задачи — решения ≤ 30 %, уроки ≤ 20 %, факты; не влезшее — оглавление до 15 строк. Бюджет по умолчанию 10 000 (сервер, MCP, CLI); хук старта сессии — 2700, потому что Claude Code режет вывод хука ≈ 10 000 символов.

##### Контекст

##### Решение

- Правила и закреплённые — целиком, но ≤ 35 % бюджета (дальше кратко, затем оглавление; проверка rules_budget в отчёте о здоровье).
- С задачей — один пул: поиск по проекту + поиск по пространствам + свежие решения/уроки как слабый сигнал; слияние рангов Σ w/(10+rank) × поправка на тип.
- Без задачи — решения ≤ 30 %, уроки ≤ 20 %, факты.
- Не влезшее — оглавление до 15 строк «id — заголовок» в резерве 10 %.
- Бюджет по умолчанию 10 000 токенов (сервер, MCP, CLI). Хук старта сессии — 2700 (≈ 9400 символов): Claude Code сворачивает вывод хука длиннее ≈ 10 000 символов в превью ~2 КБ.

##### Альтернативы

- Только квоты разделов — задача не влияет на выбор решений.
- Только поднять бюджет — откладывает проблему; на 10 000 в крупные проекты всё равно по 12 записей в оглавлении (упираются квоты типов).
- Двухшаговый контекст — больше вызовов, зависит от дисциплины агента.

##### Последствия

Ответ MCP на 10 000 оценочных токенов может превысить порог предупреждения Claude Code (10 000 настоящих токенов), но не предел 25 000.

<a id="01a1ed3a-1507-7900-b49d-ce48e19c3281"></a>
### Галактика: масса = объём текста, неявные связи по TF-IDF считаются в API при чтении и служат слабой гравитацией

<sub>`01a1ed3a-1507-7900-b49d-ce48e19c3281` · обновлено 2026-11-18 · теги: web-ui, galaxy, graph</sub>

> GET /v1/graph отдаёт mass узлов и affinity — неявные связи по TF-IDF (лексемы search_tsv, редкие теги, source_ref), считаются при чтении. Физика в galaxyModel.ts: радиус ∝ ∛mass, связи — гравитация с инерцией, связанные группы, Кеплер. Вес системы Φ = M/1000·(1 + связность); самая тяжёлая — ядро, тяжёлые тонут к центру, межпроектные связи сближают, системы обращаются по Кеплеру с вложенным весом полосами без столкновений; потенциал виден колодцем под галактикой. Межпроектные связи — один тусклый цвет без искр.

##### Контекст

В крупном проекте 371 живая запись и около 4 живых явных связей (остальные — supersedes от разбора дублей), теги в основном служебные (repo-md, cursor-transcript). Галактика показывала облако без структуры. Владелец базы: каждое знание так или иначе связано с чем-то, размер планеты должен отражать объём знания, а вес системы — управлять физикой между системами.

##### Решение

GET /v1/graph отдаёт у узлов mass (символы заголовка, summary и body) и affinity — неявные связи {from, to, score}: TF-IDF-косинус по 48 характерным лексемам из search_tsv (заголовок ×4, summary ×2) плюс редкие теги и source_ref (тот же документ или чат, та же папка) с весом ×2. Связи внутри пространства, свой проект ×1,3; до 3 соседей со score ≥ 0,12, запись без живой явной связи всегда получает ближайшего соседа; пары с явной связью пропускаются. Считается при чтении (~120 мс SQL на 720 записей), не хранится.

Физика — web/src/components/galaxyModel.ts:
- внутри системы: радиус ∝ ∛mass, звезда весит как все её планеты; явные связи тянут сильно, неявные — 0,18 + 0,9·score; сила сдвигает запись обратно пропорционально √mass; записи с притяжением ≥ 0,36 — связанные группы (label propagation), летят одним телом с приливным захватом; свободные планеты — по Кеплеру;
- между системами: вес Φ = M/1000 · (1 + U/n), U — сумма сил связей внутри системы. Самая тяжёлая — ядро в центре; тяга к ядру ∝ √Φ (тяжёлые тонут внутрь, лёгкие несвязанные — на окраине), межпроектные связи сближают, зазор между системами ≥ 24, тяжёлые сдвигаются меньше. Системы обращаются вокруг ядра по Кеплеру с весом внутри орбиты; системы с пересекающимися кольцами орбит образуют полосу с общей ω, поэтому не проходят друг сквозь друга;
- потенциал Σ √Φ·s/√(d²+s²) (s — 0,7 радиуса системы) рисуется сеткой-колодцем под галактикой (переключатель «гравитация»).

Межпроектные связи (явные и неявные) — один приглушённый цвет без искр, ярче только при выборе их звезды или планеты: иначе галактика сливается в комок.

##### Альтернативы

- Хранить неявные связи в entry_links автоматически — отвергнуто: связи ставит агент или человек, автосвязи засорили бы граф и отчёт о здоровье
- Embeddings — отвергнуто: по eval не нужны, TF-IDF по search_tsv даёт осмысленные пары
- Считать близость в браузере — отвергнуто: у клиента нет текстов
- Твёрдое вращение диска системы — заменено Кеплером и связанными группами
- Ньютоновская гравитация с Φ напрямую — отвергнуто: крупный проект тяжелее мелких систем в 3000 раз и стянул бы всё; используется √Φ
- Индивидуальный Кеплер для каждой системы — отвергнуто: системы на близких радиусах проходили бы сквозь друг друга; полосы с общей ω

##### Последствия

На 2026-11-18: 1338 неявных связей, без связей 1 запись из 720, 136 связанных групп; Φ крупный проект ≈ 3286 (ядро), проект поменьше ≈ 1182; за час симуляции зазор между системами не меньше 24. Неявная линия внутри системы тускнеет при растяжении. Раскладку можно проверить без браузера: собрать galaxyModel.ts через esbuild под node и отрисовать сверху.

### Импорт знаний из Cursor: только compaction summary, не сырые логи

<sub>`01a1e8bc-bb65-7425-99a3-7fa1f61e4910` · обновлено 2026-11-17 · теги: cursor-transcript, kn</sub>

> Выжимки из compaction → kn; jsonl и vscdb остаются локальным архивом.

При переносе знаний из Cursor в kn:

1. **Не импортировать** сырые `.jsonl`, `state.vscdb`, `agentKv` и verbatim compaction.
2. **Приоритет:** секции `## Summary (curated by compaction step)` → lesson / fact / note.

### ChatGPT подключается к kn только через OpenAI Secure MCP Tunnel: удалённый MCP, авторизация OAuth или никакая

### PostgreSQL: INSERT ... ON CONFLICT DO UPDATE требует право UPDATE, даже без конфликта

<sub>`01a1e80e-0aa2-7f33-afd9-0ed4ea2fd203` · обновлено 2026-11-17 · теги: postgres, permissions, testing</sub>

### Регулярка с \b не ловит DB_PASSWORD: между _ и буквой нет границы слова

<sub>`01a1e80e-0aba-73cc-be28-3807ffb1f67c` · обновлено 2026-11-17 · теги: regex, security</sub>

> \bpassword не совпадает внутри DB_PASSWORD, потому что _ — символ слова. Вместо \b слева: (?:^|[^a-z0-9]), справа — разрешить суффикс [a-z0-9_]*.

Правило сканера секретов `(?i)\b(password|secret|token|...)\b\s*[:=]` пропускало `DB_PASSWORD="..."` и `secret_key=...`. Исправленный шаблон:

```
(?i)(?:^|[^a-z0-9])(password|passwd|pwd|secret|token|api[_-]?key|access[_-]?key)[a-z0-9_]*["']?\s*[:=]\s*["']?([^\s"',;]{8,})
```

Плюс фильтр плейсхолдеров (`${...}`, `<your-key>`, `changeme`) и порог энтропии значения ≥ 3.0 бит/символ. Нашлось unit-тестом с корпусом положительных и отрицательных примеров.

### PostgreSQL btrim срезает только пробелы: нормализовать текст как btrim(regexp_replace(body, '\s+', ' ', 'g'))

<sub>`01a1e9c1-146c-7bdb-8d84-b322c2c58828` · обновлено 2026-11-17 · теги: postgres, quality, go</sub>

> btrim(text) без второго аргумента убирает только пробелы, не переводы строк. Для сравнения текстов сначала схлопнуть все пробельные символы через regexp_replace, потом btrim — иначе копии с \n в конце не совпадают.

В детекторе дублей хэш считался как `md5(regexp_replace(btrim(body), '\s+', ' ', 'g'))`. Копия текста с переводом строки в конце давала другой хэш: `btrim` оставил `\n`, а схлопывание превратило ` \n` в лишний пробел в конце. Интеграционный тест (три копии с разным форматированием) нашёл только две.

Правильно: `md5(btrim(regexp_replace(body, '\s+', ' ', 'g')))`.

Попутно: в Go-строке в кавычках `'\s+'` — недопустимая escape-последовательность; SQL с регулярками писать в raw-строках (обратные кавычки).
