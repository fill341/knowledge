# KN → Knowledge Operating System: аудит и roadmap

Аудит от 2026-11-17: по коду (`main`, коммит `c698d25`) и по рабочей базе (только чтение).

## 1. Текущее состояние

| Область | Состояние |
|---------|-----------|
| Хранилище | PostgreSQL 17, одна БД, пространства `personal` / `work` / `shared`, 9 проектов |
| Объём | 842 активные записи (0 на проверке, 0 устаревших/заменённых/архивных) |
| Авторы | `me` 461 (импорт документов), `cursor@personal` 325, `claude-code@work` 34, `claude-code@personal` 22 |
| Связи | 47 связей; хотя бы одна связь у 65 записей из 842 (7,7 %); `contradicts` — 0 |
| Поиск | FTS `russian` + pg_trgm; в аудите 286 поисков, 9,8 % без результатов; 66 вызовов контекста, 4,5 % пустых |
| Сессии | 35 сессий агентов, 3 не закрыты |
| Изоляция | Проверена на данных: записи `claude-code@work` только в `work`, токены агентов без доступа к чужому профилю |

## 2. Что реализовано и работает

- Жизненный цикл `draft → proposed → active → deprecated / superseded → archived` с правилами переходов по роли
  (агенты не одобряют и не архивируют подтверждённое), история версий триггером, откат, запрет `DELETE` правами БД.
- Качество при записи: JSON Schema по типу, сканер секретов, обязательный провенанс для агентов, точные дубли по
  `content_hash` (тип + заголовок + текст), предупреждение о похожих заголовках, review для решений/правил/фактов агентов.
- Контекст: детерминированный упаковщик под бюджет токенов (правила → решения → уроки → связанное по задаче).
- Граф: 6 типов связей, `supersedes` при переходе в `superseded`, 3D-карта в UI.
- Аудит всех изменений, поисков (хэш запроса и число результатов), неудачных входов.
- Интеграции: Claude Code, Cursor, Codex, ChatGPT (туннель), CLI, веб-интерфейс.

## 3. Чего не хватает

| Направление | Нет |
|-------------|-----|
| Качество и целостность | Обнаружения дублей по содержимому (дедуп учитывает заголовок), противоречий, зависимостей от устаревших знаний, «сирот», слабых записей |
| Жизненный цикл | Сроков актуальности: `review_after` не задан ни у одной записи; разделения «проверенный факт / предположение агента» (есть только `confidence`, заполнен у 44) |
| Контекст | Измерения качества retrieval (нет тестового набора запросов), объяснения, почему запись попала в контекст |
| Обратная связь | Учёта, какие знания реально пригодились (нет сигнала «использовано») |
| Сессии | Структуры итогов (цель / сделано / решения / коммиты / открытые вопросы / следующие шаги) и продолжения работы следующим агентом |
| Граф | Поиска изолированных записей, анализа влияния изменения решения, предложений связей |
| Skills | Генерации agent skills из подтверждённых знаний |
| Здоровье | Регулярного отчёта и трендов |

## 4. Главные риски деградации (измерено)

1. **Дубли по содержимому.** 181 группа записей с одинаковым текстом: 364 записи, из них 183 — лишние копии (22 % живых
   записей). Причина — двойной импорт
   документов (`docs/x.md` и `repo-md:my-app/docs/x.md`). Существующий дедуп их не ловит: в `content_hash` входит
   заголовок. Поиск возвращает пары одинаковых результатов и съедает бюджет контекста.
2. **104 несвязанные пары почти одинаковых заголовков** с разным текстом (сходство ≥ 0,8, тот же тип и пространство).
3. **Актуальность не отслеживается**: ни одной записи с `review_after`, ни одной устаревшей. С ростом базы старые факты
   будут выдаваться наравне с новыми.
4. **Граф почти пуст** (7,7 % записей со связями) — противоречия и зависимости невидимы.
5. **Незакрытые сессии** — итог работы не попадает в базу.

## 5. Архитектурные узкие места

- Дедупликация только точная и с заголовком; нет понятия «одно знание — несколько копий».
- Нет обратного сигнала об использовании: аудит знает, что был поиск, но не знает, какие записи пригодились.
- Поиск без тестового набора — улучшения нельзя доказать, деградацию нельзя заметить.
- `session_log` — свободный текст, следующему агенту нечего «подхватить» программно.

   рискованных токенов; рекомендации и безопасные действия с подтверждением человека (заменить дубли, связать).
2. ✅ **Дедупликация по содержимому при записи** (этап 2): предупреждать (не блокировать) при совпадении текста с живой записью
   другого заголовка; разобрать существующие 181 группу через отчёт.

### P1 — измеримое качество retrieval
3. ✅ **Тестовый набор запросов и `kn eval`** (этап 3): запросы с ожидаемыми записями, метрики recall@k / MRR, базовая линия текущего

## 8. Этап 2 — дубли по содержимому при записи ✅ (2026-11-17)

- Миграция `0004_body_hash`: функция `kn_body_hash(body)` (md5 текста со схлопнутыми пробелами, `NULL` для текстов
  короче 200 символов), generated-колонка `entries.body_hash`, неуникальный частичный индекс по живым записям.
- Запись и правка текста: тот же текст в живой записи пространства → предупреждение `duplicate_content` со ссылкой на
  оригинал. Запись сохраняется: копии между пространствами (promote) законны, решает человек. Для скриптов импорта —
  `"on_duplicate_content": "reject"` → `409 duplicate_content` + `existing_id`.
- MCP `kn_save` / `kn_record_decision` / `kn_update`: агенту прямо пишется «обнови существующую запись (kn_update)».
- Очередь проверки: поле `duplicate_of` и красная плашка «Такой же текст уже есть» в веб-интерфейсе и `kn review`.
- `POST /v1/import`: отчёт `duplicates[]` всегда, пропуск — по `skip_duplicate_content=true` (`kn import
  --skip-duplicate-content`, галочка на странице «Экспорт и импорт»). По умолчанию выключено: восстановление выгрузки
  должно воспроизводить её точно.
- Детекторы отчёта о здоровье перешли на `body_hash` (индекс).
- Тест `TestDuplicateContentOnWrite`: форматирование, другое пространство, короткие тексты, правка, reject, очередь
  проверки, импорт.

После разбора дублей человеком: 673 живые записи, осталось 7 групп копий, балл 76/100.

## 9. Этап 3 — оценка поиска `kn eval` ✅ (2026-11-17)

- `POST /v1/eval`: набор запросов с ожидаемыми записями (по `id`, `source_ref` или заголовку) прогоняется через тот же
  код поиска и контекста, что у агентов, в пределах видимости вызывающего. Метрики: recall@5, recall@k, MRR, доля
  пустых, попадание в контекст. В аудит — одно событие `eval`, поиски не засчитываются.
- `kn eval`: печать промахов с тем, что оказалось выше; сравнение с базовой линией; код выхода 1 при просадке
  больше допуска; `--save-baseline`. Формат и правила разметки — [eval/README.md](../eval/README.md).
- Фикстура в `make test` (`testdata/eval_fixture.json`): 13 запросов, порог регрессии `min`; ошибки разметки и
  изоляция (чужое пространство неотличимо от несуществующей записи).
- Рабочий набор `eval/local/queries.json`: 34 запроса по 10 проектам, сформулированы как задача или симптом.
  Разметка — черновик Claude, требует проверки человеком.

**Базовая линия FTS на рабочей базе (34 запроса):**

| Метрика | Значение |
|---|---|
| recall@5 / recall@10 | 0,382 / 0,382 |
| MRR | 0,314 |
| Пустых ответов | 52,9 % |
| Ожидаемое в `kn_context` (26 запросов) | 0,846 |

**Вывод.** Поиск по фразе на естественном языке — главное слабое место: `plainto_tsquery` требует совпадения всех
слов, поэтому запрос из 6–8 слов почти всегда пуст (в фикстуре — «как хранить суммы денег» при записи «Деньги храним…»;
«денег» и «деньги» ещё и дают разные основы). Контекст спасает ситуацию, потому что берёт решения и уроки проекта
целиком, а не по запросу. Низкая доля пустых поисков в аудите (9,8 %) объясняется тем, что агенты ищут короткими
ключевыми словами.

**Следующий шаг (до embeddings):** если AND-запрос дал мало результатов, повторять его как OR с ранжированием по
`ts_rank_cd` (и/или по числу совпавших слов), затем мерить `kn eval`. Принимать изменение только при росте recall
на рабочем наборе без просадки фикстуры.

## 10. Этап 4 — поиск по части слов ✅ (2026-11-17)

Если поиск по всем словам (`websearch_to_tsquery`) дал меньше 3 записей, первая страница дополняется до 3 записями
с похожим заголовком, затем записями с любым словом запроса. Они ранжируются по доле совпавших слов в квадрате;
совпадение только в теле весит половину. Запросы с операторами не расширяются. Время ответа на рабочей базе — 15–25 мс.

Каждый вариант мерился `kn eval` (рабочий набор, 34 запроса):

| Вариант | recall@5 | recall@10 | MRR | пустых | контекст |
|---|---|---|---|---|---|
| Только все слова (было) | 0,382 | 0,382 | 0,314 | 52,9 % | 0,846 |
| + любое слово, затем заголовки | 0,676 | 0,735 | 0,491 | 14,7 % | 0,923 |
| + заголовки, затем любое слово | 0,706 | 0,765 | 0,521 | 14,7 % | 0,923 |
| + вес «заголовок/суть ×2 к телу» | 0,676 | 0,794 | 0,554 | 14,7 % | 0,923 |
| + операторы по исходному тексту (принят) | **0,794** | **0,941** | **0,677** | **0 %** | **0,962** |

Вариант 2 давал регрессию: правило про порядок документации одного из проектов находилось по заголовку на 2-м месте, а после
изменения выпадало. Вариант 3 её убрал. Вариант 4 поднял recall@10 и MRR ценой одного запроса в top-5 и вдвое
сократил случаи, когда наверх вылезает длинный `fragile-invariants.md`. Вариант 5 исправил баг: слово через дефис
(«офлайн-режим», «whs-monorepo») PostgreSQL разбирает во фразу с `<->`, и проверка «есть ли в запросе операторы»
по разобранному запросу ошибочно отключала фолбэк. Теперь операторы ищутся в исходном тексте (кавычки, `-слово`, `or`).

Фикстура (14 запросов, добавлен случай с дефисом): 0,727 → 0,917 recall, 0,727 → 0,875 MRR; порог регрессии поднят. Старая базовая линия —
`eval/local/baseline-fts-and-only.json`.

**Оставшиеся промахи** (2 из 34): «ClubGG ошибка -350001» — код ошибки с минусом синтаксически является исключением
(искать как `"-350001"` или без минуса); «gh возвращает 404 на репозиторий проекта» — нужная запись проигрывает длинным
документам. Embeddings сейчас не нужны: recall@10 0,94 на полнотекстовом поиске. Следующее по качеству поиска —
расширить рабочий набор (34 запроса — мало: один запрос = 0,03) и проверить разметку человеком.

## 11. Этап 5 — сигнал «знание пригодилось» ✅ (2026-11-17)

ADR-9. Миграция `0005_entry_usage`: дневные счётчики по записи — `shown` (в поиске), `delivered` (в `kn_context`),
`opened` (полное чтение `GET /v1/entries/{id}`: `kn_get`, страница записи). Без принципала и текста запроса.
Не считаются `kn eval`, отчёт о здоровье, экспорт, чтение связей и отказы в доступе.

- Карточка записи (веб, `kn get`, API): использование за 30 дней.
- Отчёт о здоровье: проверка `unused` — активные решения, правила, уроки и факты старше 30 дней без единого показа,
  попадания в контекст или открытия за 30 дней. Включается после 14 дней сбора, до этого — «сбор идёт с …».
- Проверка `retrieval`: число повторяющихся поисков без ответа (тот же хэш запроса ≥ 2 раз за 30 дней).
- Тест `TestUsageSignal`: каждый счётчик, исключения (eval, связи, отказ в доступе), проверка `unused` на
  состаренных данных, изоляция, повторяющиеся пустые поиски.

Сбор начат 2026-11-17; первая оценка невостребованных знаний — с 2026-12-01.

**Потом, по данным:** буст ранжирования по `opened`/`delivered` — только через `kn eval` (риск «популярное
становится популярнее»); сравнение «показана vs открыта» как сигнал плохого заголовка или сути.

## 12. Этап 6 — переполнение контекста ✅ (2026-11-17)

Попутно (2026-11-17): проект определяется и у репозиториев без git remote — по пути корня (`file:///…`), через

## 14. Этапы 8–11 — P2 и P3 ✅ (2026-11-17)
