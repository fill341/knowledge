# План MVP

**Цель MVP:** Claude Code (первый агент) в реальной работе получает контекст проекта в начале сессии, находит прошлые
решения и сохраняет новые знания; Work-агент не видит Personal; данные бэкапятся и экспортируются.

**Не входит в MVP:** embeddings и RAG, Web UI, двусторонняя синхронизация с Obsidian, RLS, глубокая интеграция с bb,
предложенные правки (proposed revisions), вложения.

Каждый шаг заканчивается чем-то работающим и проверяемым.

## Шаг 0. Фундамент

- Структура репозитория, `go.work`, модули `services/knowledge-api`, `services/mcp-server`, `pkg/kclient`, `cli/kn`.
- `Makefile`, `.gitignore` (`deploy/secrets/`, `deploy/backups/`), `make secrets`.
- `deploy/docker-compose.yml`: `postgres` + `backup`; `01-roles.sh`.
- Миграции `0001_init.sql` (схема из [data-model.md](data-model.md)) и `0002_seed.sql` (пространства, `me`, типы записей).

**Готово, когда:** `make up` поднимает БД; миграции применяются с нуля; `kn_app` не может `DELETE FROM entries`
(проверено вручную); появляется дамп; `scripts/restore.sh` восстанавливает его в чистый volume.

## Шаг 1. Контракт

- `api/openapi.yaml` для эндпоинтов MVP: `me`, `spaces`, `projects` (+ `resolve`), `entries` (CRUD, `transition`, `versions`, `revert`, `links`), `search`, `context`, `sessions`, `review-queue`/`review`, `export` (jsonl, markdown), `admin/tokens`, `admin/principals`.
- Генерация: strict-server интерфейсы (`oapi-codegen`) и клиент `pkg/kclient`.
- `redocly lint` в `make lint`.

**Готово, когда:** контракт проходит линт, `make gen` даёт компилирующиеся сервер-заглушки и клиент.
Контракт ревьюится до начала реализации — дальше меняется только осознанно.

## Шаг 2. Ядро knowledge-api

- `kn-api serve | migrate | token create | healthcheck`; конфиг из env и `*_FILE`.
- Аутентификация (токены, hash, отзыв, срок), scope'ы, middleware.
- Store-слой на `sqlc`, все функции чтения требуют `Scope`.
- Spaces, projects, entries: создание, чтение, список, `PATCH` с `If-Match`, переходы статусов, версии, `revert`, связи.
- Аудит всех изменений, `Idempotency-Key`, problem+json ошибки.
- `knowledge-api` и `migrate` в compose; distroless-образ.

**Готово, когда:** интеграционные тесты на `testcontainers-go` зелёные, включая **тесты изоляции** из
[security.md §2](security.md#где-проверяются-права), конфликт версий (`412`), запрет переходов, запись версий триггером.

## Шаг 3. Качество записей

- JSON Schema для `attributes` по `entry_kinds`.
- Сканер секретов (набор правил из [security.md §5](security.md#5-сканер-секретов-в-записях)) + тест-корпус положительных/отрицательных примеров.
- Дедупликация: `content_hash` → `409`; триграммное сходство → `warnings`.
- Правило статуса: агент + тип с review → `proposed`; review-очередь, `approve`/`reject`.
- Rate limit на запись.

**Готово, когда:** запись с `ghp_...` в теле отклоняется; повтор той же записи → `409` с `existing_id`;
решение от агентского токена попадает в очередь review, а не в контекст.

## Шаг 4. Поиск и контекст

- `POST /v1/search`: FTS (`russian`), фильтры, ранжирование, `ts_headline`, триграммный добор.
- `POST /v1/context`: алгоритм из [api.md §4](api.md#4-формирование-контекста), упаковка в бюджет, markdown-вывод.
- Seed-набор из ~50 реальных записей (решения/уроки из текущих проектов) для ручной оценки.

**Готово, когда:** на seed-наборе по 10 типовым запросам (на русском и английском) нужная запись в топ-3 хотя бы в 8 случаях;
контекст укладывается в `max_tokens` и всегда содержит `pinned`-правила.

## Шаг 5. kn CLI

- `kn me | search | get | save | context | review | export | import | token`.
- Токен из Keychain (`security`), `--json` для скриптов.
- `kn context --repo-from-cwd` для хуков.
- `make token` — выпуск токена агенту и запись в Keychain одной командой.

**Готово, когда:** весь сценарий из [deployment.md §6](deployment.md#6-первый-запуск) проходит; `kn review` позволяет разобрать очередь.

## Шаг 6. MCP-сервер и адаптер Claude Code

- `kn-mcp` (stdio) на официальном Go SDK: 8 инструментов из [agent-integration.md §2](agent-integration.md#инструменты), автоопределение проекта, ленивая сессия, человеко-читаемые ошибки.
- `scripts/kn-mcp-launch`.
- `adapters/claude-code/`: команда подключения, `SessionStart`-хук, фрагмент `CLAUDE.md`; `adapters/common/AGENTS.snippet.md`.

**Готово, когда:** в реальной сессии Claude Code в рабочем репозитории контекст приходит при старте; агент сам находит
прошлое решение через `kn_search`; новое решение сохраняется с провенансом (`session_id`, `source_ref`) и появляется в `kn review`.

## Шаг 7. Остальные агенты и экспорт

- `adapters/cursor/`, `adapters/codex/` — конфиги и инструкции, проверка в реальной сессии каждого.
- `adapters/bb/` — токены `bb@personal`, `bb@work`; проброс конфигурации `kn-mcp` в агентов профиля (по устройству bb).
- Экспорт: `jsonl` (полный, с историей опционально) и `markdown`/Obsidian-формат (только чтение).
- `import` из JSONL с `dry_run`.

**Готово, когда:** экспорт → импорт в пустую БД даёт идентичные записи; vault открывается в Obsidian со связями;
агент в Work-профиле bb не находит personal-записи.

## Шаг 8. Эксплуатация и решение о дальнейшем

- 2–4 недели реального использования.
- Еженедельно: разбор review-очереди, просмотр аудита.
- Метрики из аудита: доля поисков без результатов, сколько записей создают агенты и какая доля отклоняется на review, какие типы реально используются.

## Бэклог после MVP (по ожидаемой ценности)

| Задача | Когда браться |
|--------|---------------|
| Row Level Security как второй рубеж изоляции | Сразу после MVP — дешёвая страховка |
| Гибридный поиск (pgvector + локальная модель эмбеддингов, RRF) | Когда метрика промахов FTS станет заметной |
| Двусторонняя синхронизация с Obsidian | Если окажется, что редактировать удобнее в Obsidian |
| Web UI (review-очередь, поиск, история, граф связей) | Когда CLI для review станет неудобен |
| Proposed revisions для правок агентов | Если агенты начнут портить подтверждённые записи |
| Напоминания по `review_after`, автоматическое `deprecated` | Когда записей станет много |
| Шифрование бэкапов (`age`) | Если бэкапы уходят за пределы машины |
| Глубокая интеграция с bb (передача контекста между агентами пайплайна) | После стабилизации API |

## Открытые вопросы

1. **bb** — как устроены профили и запуск агентов (откуда берутся их MCP-конфиги)? Определяет шаг 7 для bb.
2. **Work-данные** — допускает ли политика работодателя хранение рабочих знаний на личной машине в общей БД, или нужен отдельный инстанс (ADR-1, запасной вариант)?
3. **Модели эмбеддингов** (фаза 3) — только локальные (Ollama) или допустим внешний API для Personal?
4. **Сколько review готов делать человек** — от этого зависит, какие типы требуют review по умолчанию.
